Which open-source engine covers what, how Night Owl uses it, and what each one can and cannot see.

Every version is declared once, in engines/engines.json. Engines without an official image (opengrep, cppcheck, lizard, nuclei) get a Dockerfile under engines/ that verifies the pinned release by SHA-256 before building.

Night Owl runs engines as separate processes or containers and never links them. That is why a GPL engine such as cppcheck does not affect Night Owl's Apache-2.0 license.

When each engine runs

Night Owl first walks your project once and works out its profile: which package managers, languages, containers and infrastructure files are present. Each engine has a cheap "does this apply?" check, so you only pay for what the project needs. Engines run in a fixed order, because some depend on others: the SBOM engine goes first, and the license and vulnerability checks read its output.

The package managers Night Owl recognises are: npm (package.json, package-lock.json, yarn.lock, pnpm-lock.yaml), PyPI (requirements.txt, poetry.lock, Pipfile.lock, uv.lock), Go (go.mod), Cargo (Cargo.lock), Maven/Gradle (pom.xml, build.gradle[.kts], gradle.lockfile), NuGet (*.csproj, packages.lock.json), RubyGems (Gemfile.lock), Packagist (composer.lock) and Pub (pubspec.lock). These folders are never walked: .git, node_modules, bin, obj, .venv, venv, __pycache__, target, dist, build, .nightowl.

How an engine is run

  • Container by default. If the tool isn't on your PATH (or you pass --container), Night Owl runs the pinned image with docker run --rm. The container gets a unique name, so a timeout can remove it; killing only the docker client would leave it running.
  • Your source is mounted read-only. Engines can read the project but cannot change it. A separate work folder is writable, and is deleted afterward.
  • On Linux, containers run as your own user, so files written to the work folder have the right owner and can be cleaned up.
  • Secrets by name only. Values such as auth tokens are passed as -e NAME and read from the environment, so they never appear in ps.
  • Pulls are resilient. A missing self-built image is built on first use, and an image pull rate-limited by Docker Hub is retried through mirror.gcr.io.
  • Failure is contained. If an engine fails or times out, you get a warning and a succeeded: false entry in the report. The other engines still finish.

The default container network is bridge, because engines such as OSV-Scanner need to reach their data sources. Trivy's IaC checks run offline against the checks built into the pinned version.

Code rules (SAST)

Night Owl ships its own Apache-2.0 rule pack, embedded in the binary (src/NightOwl.Engines/Rules). The full list is in the Rule catalog:

  • Pattern rules find risky constructs: SQL and command injection, eval, insecure deserialization, disabled TLS validation, XSS sinks, weak hashes, and unsafe C string/format/command APIs.
  • Taint rules follow data from where it enters (an HTTP request) to where it is dangerous (a SQL query, a shell, a file path, an HTML response). They cover Flask/Django, Express, ASP.NET Core, servlets, net/http, Spring, Rails and PHP. A sanitizer such as int() or parseInt ends the flow, so a hit is a real data path rather than a guess.

Semgrep's registry rules are deliberately not used, because their license forbids bundling them in a competing tool. You can add your own Opengrep/Semgrep-syntax rules with --rules path/to/rules.

C and C++

cppcheck needs no build system or compile database. Findings are graded by how dangerous the defect is:

DefectSeverity

Opengrep's C rules add strcpy/sprintf/gets, non-constant format strings, and system() with runtime strings.

Container images

Night Owl finds the final-stage base image of every Dockerfile (resolving ARG defaults, skipping build stages and scratch) and scans it with Trivy, plus any image you pass with --image. Only vulnerabilities that have a fix are reported unless you pass --image-include-unfixed. Trivy's vulnerability database is cached in ~/.nightowl/cache.

Infrastructure as code

Trivy runs whenever the project has Terraform, a Dockerfile, a Helm chart or a compose file, or YAML/JSON that looks like Kubernetes, CloudFormation or ARM (detected by peeking at file contents). It uses the checks built into the pinned Trivy version, so results change only when the engine manifest moves Trivy forward, and the scan works offline.

Secrets

gitleaks' raw report contains the secrets, so Night Owl parses it and deletes it immediately. Findings keep only a hash of the value (for a stable ID) and the first 4 characters.

In a git repository, the full history is scanned by default:

  • A secret in both current files and history becomes one finding that notes the commit that first added it.
  • A secret that was deleted but still lives in history gets its own "Secret in git history" finding. Anyone with a clone can still read it, so the fix is to rotate the key, not just delete the line.
  • AWS's published ...EXAMPLE keys are ignored.

Code quality

lizard reports functions over the complexity limit and duplicated blocks as quality findings. Project totals (average and highest complexity, duplication rate, line coverage) appear in the CLI, the PR summary and the dashboard.
