Worked example

One small project, scanned for real. Every output on this page was captured from an actual run, so you can see exactly what Night Owl prints and what to do about each line.

The project we scan

A tiny Flask app with a lockfile and one test file. It is deliberately bad:

demo/
├── src/app.py             # a Flask app with two problems
├── tests/test_config.py   # contains a fake-looking AWS key
├── package.json           # depends on lodash 4.17.15 (old)
└── package-lock.json

src/app.py:

import os, subprocess
from flask import Flask, request

app = Flask(__name__)

@app.route("/ping")
def ping():
    host = request.args.get("host")
    return subprocess.check_output("ping -c 1 " + host, shell=True)   # line 9

@app.route("/hash")
def h():
    import hashlib
    return hashlib.md5(request.args.get("v").encode()).hexdigest()    # line 14

Line 9 runs a shell command containing text straight from the URL: /ping?host=x;cat /etc/passwd would run cat on your server. That is command injection.

Step 1: run the scan

nightowl scan demo --history off

(--history off skips git-history secret scanning to keep this example short.)

Read each column left to right: severity, category, the rule or advisory id, a plain-English title, and the location. Then the flags:

What you seeWhat it means
→ fix: 4.17.21The smallest released version that fixes this advisory. Several lodash advisories ask for different versions, and nightowl fix picks the one version that satisfies all of them.
[not imported directly]No source file imports lodash. The risk is lower, but it is only a hint. Why
[test]The file is in a test folder. It's listed, but doesn't fail the gate by default.

The verdict

Not gating: 1 in test files (still listed). Use --include-context or gate.include-contexts to gate them.
  note: 1 of these are secrets. Fake test keys are common, but a real one committed in tests is still leaked: review them.
Quality gate FAILED: 4 finding(s) at or above the policy threshold (high).

Five findings are High. Four of them count, and the fifth (the key in tests/) is held out. The command exits with code 1, so CI would stop here. The note about secrets is deliberate: the tool tells you it left a secret out of the gate so you can check that it really is fake.

Step 2: fix what's real

The dependency findings

All five lodash advisories can be cleared by one upgrade. Check the plan first:

nightowl fix demo --dry-run
  lodash 4.18.0 has its own advisories; trying 4.18.1
1 upgrade(s):
  High     npm       lodash 4.17.15 → 4.18.1  (GHSA-35jh-r3h4-6jhm, GHSA-p6mc-m468-83gw, GHSA-r5fr-rjxr-66jc, GHSA-xxjr-mmjv-4gpg, GHSA-29mw-wpgm-hmr9)

Notice the first line. The newest fix named by the advisories was 4.18.0, but Night Owl checked that version against OSV and found it has advisories of its own, so it moved up to 4.18.1. A naive "upgrade to the fixed version" would have swapped one vulnerability for another. When you are happy with the plan, apply it:

nightowl fix demo --pr      # commit to a branch and open a pull request

The command injection

Never build a shell string from request data. Pass an argument list and no shell:

@app.route("/ping")
def ping():
    host = request.args.get("host", "")
    if not re.fullmatch(r"[A-Za-z0-9.-]{1,253}", host):
        abort(400)
    return subprocess.check_output(["ping", "-c", "1", host])

The finding stops firing: there is no shell, and the value is checked before use. Rescan to confirm.

The weak hash

MD5 is fine for cache keys, but not for security. If this is a cache key, say so and accept it (next step). If it protects anything, switch to SHA-256.

Step 3: record decisions you won't fix

Say the MD5 here only names a cache entry. Mark it with a reason, so the next person understands why it's still there:

nightowl triage <id> false-positive --reason "MD5 is a non-security cache key" --shared

Find the <id> with --format json (the id field of the finding). The command writes to .nightowl/triage.json, which you commit:

[
  {
    "findingId": "…",
    "state": "false-positive",
    "reason": "MD5 is a non-security cache key",
    "at": "2026-11-17T…",
    "title": "MD5 and SHA-1 are broken for security purposes…"
  }
]

Because the id comes from the rule, file and normalized snippet (not the line number), the decision survives edits elsewhere in the file. A false positive no longer fails the gate.

Step 4: write the team's rules down

cd demo
nightowl policy init
nightowl policy validate
.nightowl/policy.yml: valid
  gate: fail on high; secret: low, quality: none
  licenses: deny (defaults), review (defaults), allow (no allow list)
  quality: coverage ≥ -, duplication ≤ -, complexity ≤ 15

The starter policy says: fail on anything high or above, fail on any secret (even low severity), and never fail on quality findings. Commit it; from now on every developer and every CI run uses these rules.

Step 5: gate pull requests on new problems only

nightowl scan . --since origin/main

Now the build fails only for findings on lines the pull request changed, or for dependency versions it introduced. Old debt is still in the report; it just doesn't block anyone.

Step 6: hand the results to other tools

nightowl scan . --format sarif --output results.sarif   # GitHub code scanning, IDEs
nightowl sbom . --vex --output sbom.vex.json            # for customers and auditors
nightowl scan . --format markdown --output summary.md   # paste into a PR

What you learned: a scan picks engines for you, merges their results into one list, and applies a gate. You can fix real problems with fix, record decisions with triage, and encode the rules in policy.yml, so CI and developers always agree.
