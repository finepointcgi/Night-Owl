How it works

A short tour of what happens between nightowl scan and the final pass or fail.

The scan pipeline

  1. Run engines. Each engine has an adapter. Independent engines are told what to scan; a failing engine becomes a warning, never a crash.
  2. Normalize. Every result becomes one Finding with the same fields: severity, category, location, rule, a stable ID.
  3. Merge. If two engines report the same problem (the same CVE, for example), you see it once.
  4. Label. Findings are tagged with their context (test, docs, production...), reachability, and your saved triage decision.
  5. Gate and report. Your policy decides pass or fail, and reports are written in the formats you asked for.

How engines are chosen

Night Owl does not ask you to configure anything. It walks the tree once, skipping folders like node_modules and .git, and notes:

  • Dependency manifests and lockfiles, and their ecosystems (npm, PyPI, Go, NuGet, Maven, Cargo, RubyGems, Packagist, Pub).
  • Source languages, from file extensions.
  • Dockerfiles, and infrastructure-as-code files.

Each engine looks at that profile and decides whether it has anything to do. The progress line » Detected: ecosystems [npm]; languages [python] is that profile. The engines page lists the exact condition for each engine. If you want to narrow it, use --engines syft,gitleaks.

Files git ignores are skipped

In a git repository, Night Owl asks git which paths it ignores (.gitignore, .git/info/exclude and your global ignore file) and tells every engine to skip them. These are build output, dependency folders, caches, and things like AI-agent worktrees: copies of your whole repository that would otherwise be scanned again and again.

It matters a lot. On a real 3,000-file .NET project that also held 150,000 ignored files, Opengrep alone went from timing out after 10 minutes to finishing in 26 seconds, and gitleaks' working-tree pass from minutes to 5 seconds. The scan prints how many paths it skipped:

» Skipping 51 path(s) that git ignores (build output, dependencies, caches)

Details worth knowing:

  • Secrets in history are still scanned. Only the working-tree pass skips ignored paths. A secret that was committed and later gitignored stays visible in the history scan.
  • Each engine gets the paths in its own format, and each path is anchored to the project root, so ignoring a top-level bin doesn't hide src/bin.
  • Outside a git repository, or if git isn't installed, only the built-in skip list applies (node_modules, bin, obj, .venv, dist, build, target, .git).

Long scans stay visible and bounded

  • Heartbeat. While an engine runs, Night Owl prints still running opengrep (60s)... every 30 seconds, so a long scan never looks hung.
  • Duplication is capped. Duplicate-code detection compares code with all other code, so its cost grows much faster than the project does. Over 25 MB of source it is skipped, and after 5 minutes it is stopped. Complexity results are kept either way, and the scan says so: note (lizard): duplication check skipped: 69 MB of source is over the 25 MB limit. The note is also recorded in the report's engines[].note.

Why order matters

Engines run from lowest order number to highest. Syft goes first because it writes an SBOM (a list of every package) into the shared scan context. License checks and the reachability analysis read that list instead of parsing the lockfiles again. The SBOM is also saved, which is what lets nightowl monitor re-check your dependencies later without rescanning.

What happens after the engines finish

  1. Merging collapses identical fingerprints (rules).
  2. Reachability marks dependency vulnerabilities whose package no source file imports.
  3. Context labelling classifies each finding's path as production, test, example, docs, generated or vendored.
  4. Ignore rules (.nightowl/ignore) drop findings in the paths you excluded. The scan says how many it dropped.
  5. Triage decisions are applied by fingerprint (shared decisions win over local ones; expired accepted risks count again).
  6. New-code filtering (--since or --baseline) narrows what the gate looks at.
  7. The gate is evaluated, reports are written, and the SBOM and a history point are saved.

Fingerprints: IDs that don't change

Triage only works if the same problem has the same ID next week. Night Owl builds IDs so they survive rescans, other engines, and code moving around:

Finding typeID is built from
Dependency vulnerabilityThe package and the canonical advisory ID (a CVE is preferred over vendor IDs)
Code findingThe rule, the file, and the normalized snippet, not the line number
SecretA hash of the secret value (the value itself is discarded)

Result: edit the file above a finding and its ID stays the same, so your "false positive" decision sticks.

To add an engine you write one class implementing IEngine and add one entry to engines/engines.json. Any engine that outputs SARIF can reuse the shared SarifParser.

What stays on your machine

  • Scans run locally in containers. Your source is not uploaded anywhere.
  • Dependency lookups send only package names and versions to OSV.dev, the same as OSV-Scanner does.
  • Secret values are never written to reports, SARIF or the dashboard. Only a hash and the first 4 characters (to recognise the key type) are kept.
  • Commit author names and emails are not stored.
  • The AI features are opt-in, and the local option (Ollama) keeps everything on the machine. See AI review and pen testing.
