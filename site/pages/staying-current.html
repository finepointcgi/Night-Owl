Staying current

Scanners are only as good as their latest rules and databases. Night Owl updates its engines automatically, and a bad update can't silently break your scans.

The big picture

1. The weekly upstream watch

A scheduled workflow (engine-watch.yml) looks for new releases of every engine and opens a pull request:

  • 14-day maturity window. It picks the newest release that is at least 14 days old. That gives the community time to spot a broken or compromised release before it reaches you.
  • It also rewrites Dockerfile pins (release hashes), rebuilds the engines, and runs the canary check.
  • Base images too. The FROM lines of Night Owl's own engine images are updated in the same PR. Versioned tags move to the newest patch of the same minor version and variant (alpine:3.24.2 to 3.24.4), so security fixes land without surprise major upgrades. Every tag is pinned by digest, so a rebuilt tag such as bookworm-slim only changes through a reviewed PR. Base images use a shorter 2-day window because official images are rebuilt often for security fixes.
nightowl engines watch --only base [--write]     # run the same check yourself

No Docker Hub pull limits

Base images are pulled through mirror.gcr.io, Google's Docker Hub cache. If a pull from Docker Hub is rate-limited (HTTP 429), Night Owl retries through the mirror. Because tags are pinned by digest the content is identical. No credentials are sent to either.

2. The signed manifest

After a merge, the engines-release workflow:

  1. builds the self-built engine images for amd64 and arm64,
  2. resolves every image to an immutable digest,
  3. runs the canary check against exactly those digests,
  4. signs the manifest (ECDSA P-256, compatible with cosign sign-blob --key), and
  5. publishes it to the engines-stable release.

3. Your machine updates itself

nightowl scan checks for a newer manifest once a day. The updater rejects:

  • unsigned or wrongly signed manifests,
  • engines without image digests,
  • unknown schema versions, and
  • anything older than what you have (rollback protection).

4. Canary check, then rollback

An update that installs is not necessarily an update that works. After installing, Night Owl scans a built-in vulnerable corpus: small files with known problems that every engine must still find. If any engine misses something, the previous manifest is restored and the bad one is skipped from then on.

nightowl canary
# Canary passed: all engines in manifest 202611170304 still find the known issues.

The same canary runs in CI on every pull request, so a broken rule or engine regression is caught before it ships.

5. Updating Night Owl itself

The signed manifest also names the latest Night Owl release, with a SHA-256 for each platform.

nightowl self-update

installs the new binary only if its hash matches. Opt out of all automatic checks with NIGHTOWL_AUTO_UPDATE=0 or --no-update.

The signing key

Installs trust exactly one public key (keys/nightowl-signing.pub), compiled into every release binary. The private half signs manifests in CI.

CopyPurpose
GitHub Actions secret NIGHTOWL_SIGNING_KEYUsed by engines-release. GitHub never shows it again once set.
An offline copy (password manager, encrypted drive)Recovery. Keep one outside GitHub.

No key rotation yet. If the key is lost or leaked, a new key means a new release and a one-time reinstall for existing users, because installs trust a single embedded key. A leaked key is serious: whoever holds it can publish a manifest that pins engine images of their choosing. Trusting a list of keys (current plus next) is on the backlog.

Setting it up for your own fork

  1. Generate a key pair: nightowl manifest keygen keys/. Commit keys/nightowl-signing.pub, and store the private key as the repository secret NIGHTOWL_SIGNING_KEY.
  2. Make the GHCR packages under nightowl-engines public after the first run, so clients can pull them.
  3. Point scripts/install.sh and ci/gitlab/nightowl.gitlab-ci.yml at your repository (the finepointcgi/Night-Owl default).
  4. Push a v* tag. The release workflow builds the binaries and refreshes the manifest; release binaries then find the manifest and public key on their own.
  5. In the repository's Actions settings, allow Actions to create pull requests, so the watch bot can open its PRs by itself.
