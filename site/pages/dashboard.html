The dashboard

A local web app over every scan you have run: an overview across projects, the history of each project, tags, and downloads of reports and STIG checklists. It reads the same files the command line writes, so there is nothing to set up.

Starting it

dotnet run --project src/NightOwl.Web

It listens on http://localhost:5212 and needs no login there. To expose it on a network address you must set NIGHTOWL_DASHBOARD_TOKEN, or turn on single sign-on; it refuses to start otherwise (details). Use --urls http://127.0.0.1:5214 to pick another port.

Overview

The first screen adds up every project you have scanned on this machine:

  • Counts of projects, critical and high findings, all open findings, and engines that failed.
  • Open findings by severity and by category.
  • Most common problems and packages to update first across all projects.
  • Projects by risk, ranked so one critical finding outweighs a pile of low ones, each with a trend line.

"Open" means a finding still needs attention: not a code-quality metric, and not triaged as a false positive or fixed. The same definition is used everywhere in the dashboard and in exports, so the numbers agree.

Projects and tags

The Projects page lists every project with its open findings, trend, quality numbers and last scan. Search by name and sort by risk, latest scan or name.

Tags group projects by team, environment or release train. Add them on a project page (type, press Enter) or from the command line:

nightowl scan . --tags prod,payments

Tags are lower-case, up to 30 characters of letters, digits and . _ : -, at most 10 per project. Click a tag to filter the list. They live in ~/.nightowl/tags.json.

Scan history, releases and change

Every scan is kept, not just the latest. On the Scans tab you can open an older scan to see the project exactly as it was (a banner makes clear it is not the latest), label scans, and compare any two.

Change is measured against a release, not the last scan

If you scan every night, "what changed since the previous scan" is nearly always "nothing", and the real drift builds up unseen. So Night Owl measures change against a baseline: a scan you have labelled, normally a release. Unlabelled scans, such as nightly runs, are never the baseline.

  • The project Summary shows "Since v1.4.0: N new, N resolved, N changed", with a link to the full list.
  • The Projects list has a "Since release" column, so you can see which project has drifted most since its last release.
  • By default the baseline is the newest labelled scan. On the Scans tab, "Measure change since" lets you pick a different release.
  • A finding triaged as a false positive counts as resolved.

How a scan gets labelled

WayHow
Automatically, at a git tagIf the repository's HEAD is exactly at a tag (a release build, for example a CI job run on v1.4.0), the scan is labelled with that tag. Nothing to configure. Nightly scans of later commits are not on a tag, so they stay unlabelled.
On the command linenightowl scan . --label v1.4.0. This wins over the automatic tag.
In the dashboard"Add label" on any row of the Scans tab. Use it to mark an existing scan as a baseline.

With no labelled scan yet, the Summary says so and tells you how to make one. In CI, add a job that runs nightowl scan when a tag is pushed; that scan becomes the release baseline.

The newest 30 scans of each project are kept, plus every labelled scan, so busy nightly runs never push a release out. Scans are stored as files under ~/.nightowl/reports/scans/. Scans made before this feature existed have no history; it starts with the next scan.

STIG checklists (.ckl)

A STIG is a DISA security checklist for a kind of system; STIG Viewer opens and fills in checklists as .ckl files. Night Owl builds one from a scan.

Set up once

  1. Download the STIG you need from DISA's public STIG library, for example the Application Security and Development STIG. It is a .zip.
  2. On the Exports page, choose Import a STIG and pick that file (the .zip or the *-xccdf.xml inside it). Night Owl checks that it really is a STIG before keeping it in ~/.nightowl/stigs/.
  3. Pick it in "STIG for checklists" and download the .ckl for any project.

Night Owl does not bundle STIG content. It reads the rules, ids and wording from the official file you give it, so the checklist always matches the STIG version you chose.

What the statuses mean

StatusMeaning
OpenScan findings clearly bear on what the rule asks. The findings are listed in the Finding Details box, and the comment says the match was automatic.
Not ReviewedEverything else. A scan finding nothing does not show a control is met, so Night Owl never marks a rule "Not a Finding" on its own.

How a finding is matched to a rule

If a rule's text names a weakness (CWE-89), findings with that CWE match. Otherwise Night Owl looks for the topic in the rule's title, discussion and check text, and matches findings of the same weakness class:

TopicMatches findings about
InjectionSQL, command, code, LDAP, XML and XPath injection (CWE-74, 77, 78, 89, 94 and related)
Cross-site scriptingCWE-79 and relatives
Path traversalCWE-22 and relatives
Embedded credentialsHard-coded secrets, and CWE-259 / 321 / 798
Weak cryptography, certificate validationBroken hashes and ciphers, and disabled TLS validation
Known vulnerabilities in componentsDependency vulnerabilities
Buffer overflow, deserialization, XXE, request forgeryTheir CWE classes

Treat it as a head start, not an assessment. The matching is keyword and weakness-class based, so it can miss a rule that is worded unusually and can occasionally match one too loosely. A person still has to review every rule in STIG Viewer before the checklist is submitted. The file follows the .ckl layout STIG Viewer 2.x reads; if your version objects to it, that is a bug worth reporting.
