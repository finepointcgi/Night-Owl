Findings and reports

Every engine speaks its own language. Night Owl translates all of them into one finding, and this page describes that shape field by field, so you can read reports, write scripts against them, and understand merging.

The finding model

FieldTypeMeaning
idstring (32 hex)Stable fingerprint. This is what triage decisions attach to.
categoryenumVulnerability, License, Secret, Code, Infrastructure, Dynamic, Quality.
severityenumCritical > High > Medium > Low > Info > Unknown. Ordered, so "high or above" is a simple comparison.
ruleIdstringThe engine's rule or advisory id: GHSA-…, CVE-…, nightowl.python.eval, secret/aws-access-token.
title, descriptionstringHuman-readable summary and details.
enginesstring[]Every engine that reported it. More than one means it was merged.
locationobjectpath, startLine, endLine, snippet. All optional (a dependency finding points at its lockfile).
packageobjectFor dependency findings: name, version, ecosystem, optional purl.
aliasesstring[]Other ids for the same issue. Vulnerabilities list the CVE here; code findings list the CWE.
fixedVersionsstring[]Package versions that fix it, when known.
referencesstring[]Advisory and commit links.
triageenumNew, Confirmed, FalsePositive, AcceptedRisk, Fixed.
contextenumProduction, Test, Example, Docs, Generated, Vendored. How it's decided.
reachabilityenumUnknown, Imported, NotImported. Dependency vulnerabilities only.
assessmentobjectPresent only with --ai: verdict, confidence, reasoning, attack path, verification steps, fix, model. Advisory.

The scan report (JSON)

--format json writes a ScanReport. The dashboard reads the same file.

FieldMeaning
projectAbsolute path that was scanned.
startedAt, secondsWhen the scan began and how long it took.
manifestSequenceThe engine manifest in use (0 if running unpinned). Lets you reproduce a scan.
engines[]One entry per engine that ran: engine, version, succeeded, seconds, error. A failed engine shows succeeded: false and its error, but the scan still completes.
findings[]The merged, sorted finding list (worst severity first, then by title).
metricsProject-wide numbers: complexity.functions, complexity.average, complexity.max, complexity.over-threshold, duplication.rate, and coverage.lines when a coverage report exists.
pentestOnly for nightowl pentest: who authorized it, the scope hash, the plan, requests sent and blocked.

Because engines[] records failures, a script can distinguish "no findings" from "the scanner did not run". Check succeeded before treating an empty list as clean.

SARIF

SARIF is the standard exchange format for static analysis, understood by GitHub code scanning and many IDEs. Night Owl maps findings like this:

Night OwlSARIF
ruleIdruleId
severity Critical or Highlevel: error
severity Mediumlevel: warning
severity Low, Info, Unknownlevel: note
idpartialFingerprints["nightowl/v1"], so code scanning tracks the same alert across runs
categoryrule tags
AI assessmentresult properties: aiExploitability, aiConfidence, aiReasoning, aiModel

Fingerprints in depth

An id is the first 32 hex characters of a SHA-256 over a few stable facts. What goes into the hash depends on the category:

CategoryHashed togetherDeliberately not included
Vulnerabilityecosystem, package name (lower-case), version, canonical advisory idThe file path, so moving a lockfile doesn't reset triage
Licenseecosystem, package, version, license id (upper-case)File path
Code, secret, IaCrule id, normalized path, normalized snippetThe line number. If there's no snippet, the line is used as a fallback.
Dynamic (DAST)rule, HTTP method, scheme+host+port+path, sorted query names, affected parameterQuery values, so a re-test with new session ids gives the same id

Normalized snippet means every run of whitespace collapses to one space, so re-indenting a line does not change the id. Changing the code itself does, which is correct: it is a different piece of code.

Canonical advisory id: when an engine reports several ids for one problem, Night Owl prefers a CVE id, then a GHSA id, then whatever it was given. Two engines that name the same bug differently therefore end up with the same fingerprint.

How duplicates merge

Findings with the same id become one. The merge rules:

  • Severity: the highest any engine gave. Engines disagree, and understating a problem is worse than overstating it.
  • Description, location, AI assessment: the first non-empty value.
  • Engines, aliases, fixed versions, references: the union (case-insensitive, no repeats).
  • The final list is sorted by severity (highest first), then by title.

Pattern and taint findings on the same line

Merging by fingerprint alone leaves one more kind of duplicate: a pattern rule and a taint rule are different rules, so they have different fingerprints, yet they often describe one bug. After the fingerprint merge, a second pass collapses them when all of these hold:

  • both are Code findings in the same file on the same start line,
  • one is a taint rule and the other a pattern rule, and
  • the taint rule's weakness class covers the pattern's. CWE-74 (injection) covers CWE-77, 78, 88, 89, 90, 94, 95, 98 and 917; CWE-22 covers 23 and 36; any other class covers only itself.

The taint finding stays, because it says more (untrusted data really arrives). It takes the worse severity, the union of engines, and the pattern rule's id and CWEs as aliases. Findings that aren't related, such as a weak hash on the same line as an injection, or an injection in a different file, are untouched. In the worked example, ten findings became nine this way.

Triage note: the absorbed finding's id disappears. A decision you recorded earlier against the pattern finding will no longer match; triage the surviving finding once.

How the gate counts findings

  1. Only findings whose triage state is New or Confirmed can block. A FalsePositive, AcceptedRisk or Fixed finding never does. An accepted risk whose --expires date has passed counts again.
  2. The threshold for a finding is the per-category value if the policy sets one, otherwise fail-on. A per-category value of none means that category never blocks.
  3. The finding must be at or above that severity.
  4. If the finding's context isn't Production (and isn't listed in include-contexts), it moves to the "Not gating" list instead of blocking.
