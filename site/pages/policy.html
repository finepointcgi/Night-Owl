Policy and gates

A quality gate is the rule that turns a list of findings into pass or fail. This page explains how to set it, and how to keep noise from blocking your team.

Policy as code

Put your team's rules in .nightowl/policy.yml and commit it. Developers and CI then always agree, because they read the same file.

nightowl policy init        # writes a commented starter file
nightowl policy validate    # checks it, shows what will apply
version: 1
gate:
  fail-on: high              # none | info | low | medium | high | critical
  per-category:              # secret, code, vulnerability, license, infrastructure, dynamic, quality
    secret: low              # any secret fails, even a low-severity one
    quality: none            # quality findings never fail the build
  ignore-unimported: false
  include-contexts: []       # test, example, docs, generated, vendored
licenses:
  deny: [AGPL-3.0-only]      # a denied license is a finding
  allow: [MIT, Apache-2.0]   # anything else is flagged for review
quality:
  min-coverage: 80
  max-complexity: 15
  max-duplication: 5

How the pieces combine

  • Precedence: command-line flag, then policy file, then built-in default.
  • An explicit --fail-on replaces the policy's gate, including its per-category rules. That is deliberate: a flag is a one-off override.
  • Each license list (deny, review, allow) replaces the built-in default for that list; it does not add to it.
  • Typos are errors. Unknown keys and bad values stop the run, so a misspelled rule can never silently switch a check off.

Not in the policy yet: required SBOM fields and a maximum age for accepted risks. Use --expires when triaging for now.

Tests, examples and docs don't fail the build

A hard-coded password in a unit test is not the same risk as one in your login code. Night Owl labels every finding by where it lives, judged from the path:

ContextExamples of what counts
productionEverything else.
testtest/, tests/, __tests__/, fixtures/, *_test.go, *.test.js, *.spec.ts, test_*.py...
exampleexamples/, samples/, demo/...
docsdocs/, *.md, *.rst...
generateddist/, generated/, *.min.js, *.pb.go, *.g.cs...
vendorednode_modules/, vendor/, third_party/, .venv/...

If a path matches more than one, the order of precedence is vendored, generated, test, example, then docs.

Everything is still listed and counted. Only production code fails the gate by default. The scan prints what was left out (Not gating: ...), and warns if any of it is a secret, because a real key committed in a test folder is still a leak.

To opt back in:

nightowl scan . --include-context test,example     # or: all
gate:
  include-contexts: [test]

On four real repositories (express, flask, gin, NodeGoat) this removed every high-severity code and secret finding that sat in tests, examples or docs, and kept all ten genuine ones in NodeGoat, which is vulnerable on purpose. The classifier only knows common folder names; for unusual layouts use .nightowl/ignore.

Gate on new code only

Turning scanning on for an old project can produce hundreds of findings. You don't have to fix them before you can use the gate.

FlagFails only on...
--since origin/mainFindings on lines the change touched, or on dependency versions it introduced.
--baseline lastFindings not seen in your previous scan. You can pass a saved report instead of last.

Existing problems stay visible in reports; they just don't block merges.

Triage that sticks

Decisions are keyed by the finding's fingerprint, so they survive rescans and code moves.

StateUse it when
false-positiveThe tool is wrong.
accepted-riskIt's real, and you've chosen to live with it. Always give --expires.
confirmedIt's real and needs fixing.
fixedYou've fixed it (it will reopen if it returns).
resetUndo a previous decision.

With --shared decisions go into .nightowl/triage.json in the repo, where they get code review like any other change.

Ignored paths

.nightowl/ignore uses gitignore-style patterns. Use it for fixtures, vendored code and deliberately vulnerable samples:

# .nightowl/ignore
tests/fixtures/
legacy/**/generated/
*.min.js

Quality gates

These come from the lizard engine and your existing coverage reports (Cobertura XML or lcov.info):

  • --min-coverage 80: fail below 80% line coverage.
  • --max-duplication 5: fail above 5% duplicated code.
  • --max-complexity 15: functions above this are reported as quality findings (Low/Medium, so they never trip the default security gate).
